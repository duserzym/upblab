# Audit 2026-11-13: database handling and interface

Scope: grainatlas, laicpmsdb, UPb Lab (upblab) and UPbRPy Studio. Read-only;
nothing else in any repository was changed. grainatlas line numbers are from
the committed `HEAD` (6f35043); another session has uncommitted changes in
`grainatlas/ui/src/lib/sync*.ts` and `laicpmsdb/service/tests/`, so working-tree
lines may differ. upblab is also being edited by the launch-button session,
so line numbers in `atlas-refresh.ts`, `App.svelte`, Home cards, `Plot.svelte`
and `Review.svelte` may have moved by a few lines. "Read" means verified by reading the code; "Ran" means
verified by running a test, script or browser check (details in the last
section).

## Summary

- The database side is sound at its core. A sync runs in one transaction
  under a mount lock, checks the base revision, refuses with a list of changes
  when another window changed the same project, and keeps an append-only change
  log. Desktop project files are saved before any sync starts.
- The three weak spots that matter most: error messages built from raw ids and
  joined into one line (D1); UPb Lab does not refresh when a standalone
  GrainAtlas window syncs, which is now the normal way of working (D2); and
  there is no backup command and no way to count mounts, grains, spots and
  links before and after a change (D3).
- Studio's database mode is implemented end to end: it opens a
  `upbr://session/<id>?server=&code=` link, redeems the code at
  `POST /v1/auth/exchange`, downloads the session bundle, and submits a
  reduction to `POST /v1/sessions/{id}/runs/import`. The installed
  `/Applications/UPbRPy Studio.app` registers the `upbr` scheme. Ran: the 37
  launch, client and database-GUI tests pass against the fake server
  (`UPbRPy/tests/test_database_gui.py:124` covers link, open, submit, prefer).
  Not verified: a real click on a link against a real laicpmsdb. On Windows
  the scheme is registered only by File > Database or
  `--register-url-scheme` (`UPbRPy/GUI/launch.py:273`), not by an installer.
- Interface: no `transition: all`, no `ease-in`, no `scale(0)`, no Svelte
  transitions, and both apps zero their `--motion` token under reduced motion.
  UPb Lab Home and Review show no sideways overflow at 1280 x 800 and
  1024 x 640 with long names and 1000 spots (Ran). The issues are smaller:
  numbers that can be cut off in grainatlas, a keyboard-triggered pulse, two
  spinners without reduced-motion handling, and pan/zoom that writes reactive
  state on every pointer event.

Counts: Part 1 has 3 high, 4 medium, 4 low. Part 2 has 0 high, 7 medium,
8 low. Total 26 findings: 3 high, 11 medium, 12 low.

## Part 1: database handling

The seven points, in short:

1. Saved locally first: yes for desktop project files (`grainatlas/ui/src/lib/actions.ts:657` saves, then 662 syncs; `.gaproj` uses temp file + rename, `tauri/src-tauri/src/lib.rs:614`). The sync draft in localStorage can fail silently (D4).
2. All or nothing: yes (`laicpmsdb/service/apps/preparation/sync.py:832` `transaction.atomic()` + `select_for_update`; validation in `_prepare` before any write; dry run rolls back at :960). Unchanged rows are not rewritten (`_save_changed`, :782). Exact replay is not recognised (D8). Image publication is a separate step (D5).
3. One bad item: the whole sync is refused, never silently, but the message is hard to read (D1, D7, D10). See question Q1.
4. Only changes: yes for uploads after the first sync (`sync.ts:122-136`, mode `delta`); the first sync sends a full snapshot of the project. Each sync downloads the project's elements twice (D9).
5. Database changed underneath: yes, a 409 with the change list opens a Mine/Database review (`sync.py:409`, `sync-session.svelte.ts:466`), but it shows raw ids and JSON (D6), and image publication bypasses it (D5).
6. UPb Lab refresh: works for the embedded GrainAtlas through `lab.atlas.synced` (`upblab/ui/src/lib/incoming.ts:59`, `atlas-refresh.ts:36`); weak for standalone windows (D2).
7. Backup and counts: missing (D3).

## Decisions (Yiming, 2026-11-13)

- Q1: valid items go through; invalid items are held back and an error
  handling flow takes the user through the list of held items to fix them.
  This replaces "a sync applies completely or not at all" for item
  validation (the valid part still applies atomically).
- Q3: both. GrainAtlas and Studio notify UPb Lab directly after a sync or
  submit, and UPb Lab also polls at a fixed rate as a fallback.
- Q4: both. Backups run automatically before maintenance commands, and
  `make backup` is available on its own.
- Q2: pixels only, warn. Publishing stores images and files (spots.json
  kept for viewing) and no longer writes spot or grain rows. When spots.json
  differs from the database, the reply says how many spots differ and
  GrainAtlas offers to sync first. Sync is the only writer of grains and
  spots; the older "Send spots" path (`POST /mounts/{id}/spots`) is retired
  or routed through sync.

## Questions for Yiming

- Q1. Points 2 and 3 pull against each other. Today one invalid grain or
  spot refuses the whole sync (all or nothing, `sync.py:570, 776`). Keep
  that, and only make the message readable (D1)? Or allow a partial sync
  that applies the valid items and holds back the invalid ones? Partial
  syncs would undo the rule that a sync applies completely or not at all.
- Q2. D5: should publishing images stop writing spot rows altogether, so
  that the sync endpoint is the only writer of grains and spots? The
  current re-import comes from the earlier design where the published
  bundle carried spots.
- Q3. D2: with editing now in separate windows, should UPb Lab poll every
  60 s while visible (one small request per mount), or should GrainAtlas
  and Studio notify UPb Lab directly (a local event, which needs new
  plumbing outside the bridge)?
- Q4. D3: should backups run automatically before every maintenance
  command (`merge_mounts`, `register_mounts`, migrations), or stay a
  manual `make backup` that you run first?
